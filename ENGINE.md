# ENGINE.md

Compagno di [AGENTS.md](AGENTS.md): quello sono le ricette, questo è la mappa dell'implementazione interna dell'Engine che i README non citano per nome. `backend/README.md` e `frontend/README.md` documentano la superficie consumabile, cioè cosa inietti, estendi, configuri; qui invece stanno i file che quella superficie la implementano, attrezzeria interna, mai un seam. Lo scopo non è invitarti a modificarli (l'Engine resta INTOCCABILE, la regola d'oro non cambia), ma farti trovare "dov'è" e "perché è fatto così" senza dover leggere il codice a freddo. Come il resto della documentazione dell'Engine, questo file si aggiorna dal template al merge: non è tuo, non lo adatti al progetto.

Se un file non compare qui né nei due README, è quasi sempre perché è a scopo singolo e il nome + il commento in testa al file bastano (es. `formatter.ts`, `validation.ts`): non serve una voce dedicata per capirlo.

## Frontend — `frontend/src/app/core/engine/`

### Pipeline SSR (`server/`)

Il Node SSR (`server.ts`) è composto da moduli a scopo singolo, ciascuno testabile/leggibile da solo:

| File | Cosa fa | Perché è fatto così |
| :--- | :--- | :--- |
| `server-env.ts` | Sorgente unica delle variabili d'ambiente, valutata **lazy** | L'import da solo non legge nessuna env var: così il build Angular (route extraction) può importare questo modulo senza che le variabili runtime esistano ancora. La validazione delle obbligatorie avviene in `server.ts` solo all'avvio reale |
| `server-paths.ts` | Risolve le cartelle fisiche (dist browser/server, cache immagini) | La cache vive fuori da `src/assets` e isolata per progetto (hash del percorso): impedisce a `ng serve` di ricaricare la pagina a ogni thumbnail generato e a più progetti sullo stesso host di mischiare le immagini |
| `security-headers.ts` | Carica `security-headers.json` (sorgente condivisa col backend) e li applica alle risposte Node | Fallback imbottito nel codice se il file manca, così il server parte comunque protetto invece di servire senza header |
| `asset-mapping.ts` / `asset-handler.ts` | Risolvono l'ID asset dichiarato in `mapping.json` al file fisico reale; rilevano se un file è un'immagine raster ridimensionabile da Sharp | Nascondono i percorsi fisici agli utenti e distinguono i formati compatibili con resize da quelli da servire tali e quali (es. SVG) |
| `image-cache.ts` | Cache su disco delle immagini ridimensionate, con tetto di dimensione (default 500 MB, `IMAGE_CACHE_MAX_MB`) e sweep LRU periodico (ogni 6h) | Evita di rigenerare ogni resize a ogni richiesta senza lasciare che la cache cresca senza limite tra un deploy e l'altro |
| `fs-utils.ts` | `fileExists()`: verifica asincrona (`access`), non `existsSync` | Un check sincrono sospenderebbe l'event loop mentre il disco risponde; l'asincrono no |
| `preview-crypto.server.ts` | Cifra (AES-GCM) il payload di `/cdn-cgi/preview` | Solo Node (mai nel bundle browser); la chiave, in ordine di fallback, è un secret esplicito → la prima API key → `nomeApp:versione` — così il blob resta non falsificabile anche senza configurare nulla |
| `server-font-metrics.ts` + `preview-builder.ts` | Deriva le metriche dei font **realmente installati** nel container (via `fc-match` + parser TTF minimale) per costruire l'SVG dell'og:image dinamica | Le tabelle di metriche baked-in andrebbero disallineate a ogni cambio di pacchetto font nel Dockerfile; leggerle dai font reali le tiene sempre corrette |
| `routes/api-proxy.ts`, `routes/cdn-asset.ts`, `routes/og-preview.ts` | Handler Express concreti dietro `/api`, `/cdn-cgi/asset`, `/cdn-cgi/preview` | Le tre route sono già descritte a alto livello nel [README root](README.md) («Route SSR speciali»); qui c'è il "come" per chi deve toccarne il comportamento |

La guardia di deriva configurazione (`scripts/config/config-fingerprint.ts`, `scripts/config/settings-merge.ts`) funziona così: `config-fingerprint.ts` calcola un hash SHA1 (12 caratteri) delle sole sezioni identity-critiche di `global-settings.json` (`project`, `Localization`, `site`, mai `.local.json`, che tocca solo segreti). `generate-statics.ts` lo scrive in `environment.ts` come `configFingerprint` a ogni build; `server.ts` lo ricalcola a runtime dal config letto da `getBr1Settings()` e confronta i due valori al boot, stampando un warning su mismatch, così il server si accorge da solo di essere partito con un `environment.ts` non rigenerato (tipico: `ng serve` lanciato bypassando `predev`/`prestart`, o `global-settings.json` modificato senza rilanciare la build). `settings-merge.ts` (`deepMergeSettings`) è il merge profondo di `global-settings.local.json` sopra il base, con la stessa semantica di `scripts/lib/br1-config.sh`, condiviso fra `server-env.ts` (lettura runtime) e `generate-statics.ts` (lettura al build, solo nel percorso file-based; l'ARG Docker `BR1_PROJECT_JSON` resta volutamente il solo file base, senza segreti). È un'unica implementazione, così le due letture non possono divergere nella semantica di fusione.

### Navigazione multilivello (`components/navbar`, `footer-nav*`, `nav-*`)

`navbar.component.ts`, `footer-nav.component.ts` + `footer-nav-group.component.ts` (footer, ricorsivo), `nav-dropdown.component.ts` + `nav-submenu.component.ts` (flyout desktop / accordion mobile della navbar) e l'atomo `nav-link.component.ts` sono la resa concreta della feature "Menu Multilivello" (già descritta a livello di configurazione in `nav.ts`/root README): la scomposizione in più componenti serve a gestire la ricorsione dei gruppi annidati senza duplicare la logica di stato attivo/hover tra footer e navbar. `back-to-top.component.ts` è indipendente, nessun legame col menu: soglia di scroll da `DesignSystemPreset.backToTopSoglia` (`BACK_TO_TOP_SOGLIA_PX`, già in `frontend/README.md`), non più fissa.

Il raggio d'angolo e l'ombra di `.dropdown-menu`/`.context-menu` (desktop) e la durata delle loro animazioni d'apertura leggono `--elevazioneRaggio`/`--shadowElevated`/`--movimentoPannello` invece di un letterale — vedi la sezione dedicata più sotto per dove quelle custom property vengono iniettate. Il raggio del pannello mobile a foglio (`.context-menu-sheet`) resta invece fisso: convenzione del pattern bottom-sheet, non un'identità di design system.

`breakpoints.ts` espone `isDesktopViewport()`, letto da `navbar.component.ts` e `nav-submenu.component.ts`: legge la custom property CSS `--bp-md` (iniettata in `_base.scss` da `lib.$bp-md`) invece di duplicare `768px` hardcoded in TS, come sorgente unica del breakpoint desktop/mobile condivisa fra SCSS e TS. Sempre in `navbar.component.ts`, oltre al limite di annidamento (`NAV_DEPTH_WARN`/`NAV_DEPTH_MAX`, già in `frontend/README.md`), c'è un limite indipendente sul numero di voci di primo livello: oltre `MAX_RECOMMENDED_TOP_LEVEL_ITEMS` (6) le voci in eccesso confluiscono in un dropdown finale "Altro", sintetico, non dichiarato in `site.ts`, con lo stesso rendering di un `addGroup`. La soglia di attivazione è deliberatamente la stessa del warning in console, così chi corregge l'avviso in dev fa sparire anche l'overflow. Misurato via `ResizeObserver` sulla larghezza reale disponibile, solo su desktop (su mobile lo stack verticale non ha bisogno di overflow).

### Effetto smoke (`components/smoke-effect/smoke-effect.component.ts`)

Il componente che renderizza l'animazione di particelle su `<canvas>`, montato da `app.component.ts` (la shell, tua) che gli passa `showSmoke` già calcolato. Il contratto che un design system scrive (`SmokePreset`, `intensita`, i default) è già interamente documentato in `frontend/README.md` («Effetto smoke: il contratto `SmokePreset`»); qui sotto solo COME quella scelta diventa i numeri grezzi che il componente consuma davvero.

`SMOKE_INTENSITY` (`design-system-presets.ts`) mappa ogni `SmokeIntensity` in `{ maximumVelocity, particleRadius, density }` — `resolveSmoke()` (`siteBuilder.ts`) legge `DesignSystemPreset.smoke.intensita` (default `'pulviscolo'`) e produce la `SmokeSettings` risolta che finisce in `SiteConfig.smoke`. Perché non esporre i 3 numeri direttamente: `maximumVelocity` viene ulteriormente scalato per `0.02` dentro `initParticles()` (componente) prima di diventare velocità reale in px/frame — un fattore interno che nessun design system dovrebbe dover conoscere per scegliere un valore sensato, da qui i 3 gradi nominati invece del numero grezzo.

### Leve nominate del design system: risoluzione (`design-system-presets.ts`, `siteBuilder.ts`, `services/appearance.service.ts`)

Il "cosa" (nomi dei campi, valori, quando usare quale) è interamente in `frontend/README.md` — «Sfondo a tinta piena», «Effetto smoke», «Altre leve delegate al design system». Qui il "come": ogni leva è un'unione letterale (`'foglio'`/`'scatto'`/`'standard'`/ecc.), mai un numero grezzo nel contratto pubblico — la traduzione in valori concreti (float, stringhe CSS, classi Bootstrap) resta un dettaglio interno, con una tabella `Record<Leva, Valore>` per leva in `design-system-presets.ts` (`VIVIDEZZA_*`, `MOVIMENTO_DURATA`, `ELEVAZIONE_TIERS`, `HOVER_INTENSITY_TIERS`, `PULSAZIONE_TIERS`, `MUTEZZA_SECONDARIO_FATTORE`, `SEPARAZIONE_SUPERFICI_FATTORE`, `CONTENT_WIDTH_CLASSES`, `BREADCRUMB_SEPARATORE`, `BACK_TO_TOP_SOGLIA_PX`) mai importata da un design system.

**`superfici` → palette (`AppearanceService.computePalette`).** `backgroundVividness` (0/0.5/1, da `superficiVividness()` in `siteBuilder.ts`) interpola in OKLCH la lucentezza (L) di ogni superficie di contenuto verso quella del colore che le governa (`liftBg()`) — un'interpolazione lineare, non un valore letterale, perché preserva l'ORDINE relativo fra le superfici (base sempre più scura di surface, di hover, ecc.) qualunque sia il grado scelto. Costo collaterale su `'tenue'`/`'fusione'`: i margini di contrasto FRA superfici si stringono, e un paio di foreground calcolati dal brand (`colorPrimary*`, più `colorSecondary`/`colorInfo` quando NON overridden) possono perdere la variante che li distingue a sufficienza e ripiegare su nero/bianco puro — mai un crash né una violazione WCAG (il testo resta sempre garantito da `findCompliantColor` contro la superficie REALE), un override "duro" (`colorSecondary` ecc. esplicito) invece NON ha questo paracadute, resta l'hex scelto anche se il risultato è illeggibile. `separazioneSuperficiFattore` è un asse indipendente sullo STESSO meccanismo: scala lo scarto fra il default-L di ogni superficie e quello della base (`separaLt`/`separaDk` in `computePalette`) PRIMA di `liftBg()` — il bordo (`colorSurfaceBorder*`) ne resta fuori di proposito, ancorato a un minimo WCAG 1.4.11 (≥3:1), non una scelta di stile. `mutezzaSecondarioFattore` scala invece il chroma del `secondary` auto-calcolato (default 0.75× il chroma del brand, tetto fisso 0.12) — indipendente da vividezza/separazione, tocca solo la saturazione di quell'unico colore.

**`movimento`/`elevazione`/`hoverIntensity`/`pulsazioneAttiva` → custom property CSS.** A differenza della palette (tone-reattiva, ricalcolata ad ogni cambio `prefers-color-scheme`), questi 4 assi dipendono solo da `ContestoSito.config` — fissa per l'intero deployment — quindi `appearance.service.ts` li calcola UNA VOLTA in una costante di modulo (`STATIC_DESIGN_VARS`, non un metodo) invece di ricalcolarli ad ogni render. Iniettati dallo stesso canale duale dei colori: `_buildThemeStyleTagFromPalette` (SSR, stringa nel tag `<style id="theme-init">`) e `_applyPalette` (client, `el.style.setProperty`) — entrambi leggono la stessa costante, non possono divergere. Le custom property risultanti (`--movimentoPagina`/`--movimentoPannello`, `--elevazioneRaggio`, `--shadowElevated`/`--shadowElevatedHover`, `--hoverBg`/`--hoverBorder`/`--activeBg`/`--activeBorder`, `--pulsazioneNome`/`--pulsazioneSpread1`/`--pulsazioneTrasparenza1`/`--pulsazioneSpread2`/`--pulsazioneTrasparenza2`) sono consumate con un fallback letterale inline in ogni SCSS che le usa (`_motion.scss`, `_dropdown.scss`, `_submenu.scss`, `context-menu-overlay.component.scss`, `image-lightbox-overlay.component.scss`, `_bootstrap-theme.scss`, `_utilities.scss`) — il fallback riproduce il comportamento storico, quindi un mancato boot di `AppearanceService` (scenario limite) non lascia mai lo stile completamente rotto. `hoverIntensity: 'decisa'` spinge più in là un trade-off d'accessibilità già presente nell'engine: in dark mode lo scurimento hover/active fa scendere il boundary TRANSITORIO sotto WCAG 1.4.11 mentre testo e stato a riposo restano sempre garantiti (commento su `.btn-primary`, `_bootstrap-theme.scss`) — non è un trade-off nuovo introdotto da questo campo, solo reso graduabile.

**Iniezione condizionata (`ssrThemeTagPresent`) e `colorTema` fisso per sessione.** `colorTema` (`site.colorTema`) è statico per l'intera sessione — non esiste (più) un modo di cambiarlo a runtime: c'era `setColorTema()`, mai chiamato da nessun consumer reale nei progetti figli (solo letto, `theme.colorTema()`, in `style-guide.component.html`/`che-faccio.component.html`), rimosso. Questo rende ridondante riapplicare le CSS custom property via `el.style.setProperty` (`_applyPalette`) quando l'SSR ha già iniettato `<style id="theme-init">`: quel tag contiene già blocchi `@media(prefers-color-scheme)` che coprono DA SOLI, in puro CSS nativo, sia il render iniziale sia ogni cambio di tono OS successivo — preferire il meccanismo nativo del framework a uno equivalente scritto a mano, stesso principio già applicato altrove nell'engine. Il costruttore di `AppearanceService` calcola `ssrThemeTagPresent` una volta (`!!document.getElementById('theme-init')`, stesso pattern già usato da `_ensureCustomFontFace`) e lo usa per saltare `_applyPalette` sia al boot sia ad ogni evento `matchMedia('(prefers-color-scheme: dark)')` — il fallback CSR-only (nessun tag SSR, es. build/preview senza SSR) continua invece ad applicare le CSS var via JS, com'era prima. Il listener OS e l'aggiornamento del signal `themeTone` restano SEMPRE attivi, mai condizionati: altri consumer (`navbar.component.html`, `notification.service.ts`) leggono `themeTone` a prescindere dal fatto che le CSS var vadano riapplicate o no. Nulla di questo tocca `computePalette` né i 4 punti che costruiscono gli `overrides` (client, `app.config.server.ts`, `og-preview.ts`, `generate-statics.ts`): quel calcolo resta identico, cambia solo QUANDO/SE il risultato viene riscritto lato client via `style.setProperty`.

**Leve per-componente**, ognuna un lookup diretto da `ContestoSito.config` a una classe/valore, nessuna computazione: `contentWidth` (`app.component.ts`, classe sulla colonna breadcrumb/pannello), `breadcrumbStile` (`breadcrumb.component.ts`, carattere separatore), `footerIdentita` (`footer.component.ts`, booleani `showSocial`/`hoursAccordion` di `app-identity-render`), `cookieReopenStile` (`cookie-banner.component.ts`, classe modificatrice `.cookie-reopen-btn--standard` — il LATO resta sempre `inset-inline-start`, opposto a `back-to-top`, in entrambi gli stili: cambiarlo raddoppierebbe la probabilità di sovrapporsi a un controllo di pagina), `badgeNotifiche` (`notification-bell.component.ts`, testo del badge svuotato + classe `--dot`), `pulsazioneAttiva` (`.pulse-live` in `_utilities.scss`, via le stesse custom property statiche di sopra).

### Overlay del menu contestuale (`components/context-menu/`)

`context-menu-overlay.component.ts` (rendering dell'overlay) e `context-menu.models.ts` (forma di `ContextMenuOption`) sono l'implementazione dietro il selettore `[appContextMenu]` (già documentato). Posizionamento, portal e dismiss-on-outside-click sono CDK Overlay/Portal (`context-menu.directive.ts`, già una dipendenza reale del progetto); la navigazione da tastiera fra le voci usa CDK `FocusKeyManager` (`@angular/cdk/a11y`) invece di un roving-focus scritto a mano — stessa libreria, nessuna dipendenza aggiuntiva.

### Notifiche/dialog (`services/notification.service.ts`) — SweetAlert2, non Bootstrap JS: valutato e scartato

`NotificationService` (alert/confirm/choose/prompt/toast/promise) resta su SweetAlert2, non su `bootstrap.Modal`/`bootstrap.Toast` — valutato esplicitamente, non per inerzia. SweetAlert2 dà gratis 4 cose che un port perderebbe o richiederebbe di riscrivere identiche a mano comunque: un'API a Promise (Bootstrap è a eventi, `shown.bs.modal`/`hidden.bs.toast`), le icone built-in (successo/errore/warning/info/domanda — Bootstrap non ne ha), un primitivo per l'input-dialog validato di `prompt()` (Bootstrap non ne ha), il pause-on-hover/focus + barra di progresso del toast (già usato per WCAG 2.2.1 — nessuna delle due librerie lo dà gratis, va scritto comunque). Il costo del bundle è sostanzialmente pari (~31KB gzip SweetAlert2 vs ~24KB gzip il bundle JS di Bootstrap, mai importato oggi). L'unico vantaggio reale di un port sarebbe il theming (il DOM nativo Bootstrap eredita `data-bs-theme` da solo, mentre oggi ogni chiamata ricostruisce `Swal.mixin({theme: ..., customClass: {...}})` da `AppearanceService.themeTone()`) — non basta a giustificare riscrivere ~10 metodi pubblici perdendo funzionalità reale. Coerente col principio guida dell'Engine ("usa il meccanismo nativo se il framework lo offre già"), ma qui il framework NON offre già l'equivalente — motivo per cui questo è un NO deliberato, non un'eccezione alla regola.

### CSP: `style-src-attr 'unsafe-inline'` — deliberato, non un gap dimenticato

`security-headers.json` (`Content-Security-Policy`) lascia `style-src-attr 'self' 'unsafe-inline'` mentre `script-src`/`style-src-elem` usano un nonce per-richiesta — valutato esplicitamente, non per disattenzione. Due motivi indipendenti, non solo l'integrazione di librerie terze (Mapbox GL JS ne è l'esempio più comune — scrive posizioni calcolate a runtime come attributi `style=""` inline, imprevedibili in anticipo): (1) CSP non offre un meccanismo a nonce/hash praticabile per gli attributi di stile inline — l'unica alternativa sarebbe `'unsafe-hashes'`, che richiede di conoscere il valore esatto della stringa in anticipo, impossibile per stili calcolati a runtime; (2) ogni binding `[style.qualcosa]` nei template Angular, durante l'SSR, viene emesso come attributo `style=""` letterale nell'HTML (nessuna CSSOM disponibile lato server) — quell'HTML iniziale è markup, quindi soggetto a `style-src-attr`: senza `'unsafe-inline'` ogni pagina con un binding `[style.x]` (diversi in questo Engine, es. `[style.height.px]`) avrebbe un flash di contenuto non stilizzato fino all'idratazione. `extendCsp` (`csp.ts`) resta comunque il punto giusto per estendere `script-src`/`connect-src`/`frame-src` ecc. con domini esterni (YouTube, Mapbox, altri) via `security-headers.override.json` — è solo `style-src-attr` specificamente a non doversi stringere.

### Direttive di rendering dichiarativo (`directives/`)

`img-render.directive.ts` e `qr-render.directive.ts` sono l'implementazione dietro `[appImgRender]`/`[appQrContent]` (selettori già documentati in `frontend/README.md`): trasformano un `<img>` nel render di un'immagine generata via `ImgBuilderService` o di un QR via `QrCodeService`.

### Interceptor errori API (`interceptors/api-error.interceptor.ts`)

Implementa il toast automatico sugli errori HTTP per le richieste non marcate `{ silent: true }` (pattern già documentato). È un interceptor Angular a sé, non più logica dentro `BaseApiService`, per tenere il client API puro (idioma Angular per i concern trasversali).

### Cookie interni (`services/cookie/`)

`cookie-type.ts` definisce `ConsentCategory` (Technical/Analytics/Profiling/TechnicalOptional), la tassonomia dietro le voci di `COOKIE_MAP` (vedi ricetta in `AGENTS.md`). Technical è l'unica esente da consenso per legge (strettamente necessaria, mai uno switch nel banner); TechnicalOptional è il suo contrario — tecnica ma non indispensabile (es. il Service Worker/PWA built-in) — trattata come Analytics/Profiling: proprio switch, proprio consenso. `cookie-utils.ts` è un check statico usato in fase di build da `siteBuilder.ts` per decidere se il sito richieda una Cookie Policy (`cookiePolicy` in `legalPages`): non è runtime, è un dettaglio di composizione del sito.

### Connessione realtime, dettaglio interno (`services/notification-connection.ts`)

Tiene il `connectionId` corrente in un signal separato da `NotificationStreamService`: permette a `BaseApiService` di leggerlo (per l'header `X-Connection-Id`) senza iniettare, e quindi senza attivare, lo stream. Finché nessuno apre lo stream resta `null`.

### Pagine legali (`legal/legal-pages.ts`)

`legalPages` (`site.ts`) è un array (`LegalPageSpec[]`, definito in `siteBuilder.ts`): un elemento per pagina, tutti con lo stesso trattamento — nessuna distinzione, né nel tipo né nel codice, fra pagine "di sistema" e pagine di progetto. `legal-pages.ts` non ha più uno slot per nome da valorizzare: `filterManagedLegalPages` (override), `buildPolicySection` (rotta `/policy/*` + `PolicyComponent`) e `legalSlugFor` (markdown) camminano tutti sulla stessa lista con un solo ciclo ciascuno.

Per le 5 pagine standard, `STANDARD_LEGAL_PAGES` (dati, in `legal-pages.ts`, riesportati da `siteBuilder.ts`) fornisce `path`/`titleKey`/`descriptionKey`/`markdownSlug` pronti: il figlio li abbina al proprio `PageType` con lo spread (`pages/policy/legal.pages.ts` nella demo). Una policy in più (es. diritto di recesso) è una voce scritta per esteso nello stesso array, senza `STANDARD_LEGAL_PAGES` a fare da scorciatoia — non c'è altro da toccare in questo file per il progetto figlio.

L'unica voce con un ruolo a runtime resta la Cookie Policy (link dal banner, obbligatoria se il sito usa cookie): non si riconosce guardando `legalPages` — è il campo separato `cookiePolicy: PageType | null` (`SiteConfig`) a dirlo. È l'unico caso speciale rimasto nel modello: ogni altra voce di `legalPages` è testo generico.

### Budget bundle iniziale (`angular.json`, `maximumWarning: 930kB`)

Il valore traccia il peso EAGER del solo Engine (shell + navbar/footer/cookie-banner/smoke-effect/
back-to-top/breadcrumb, Bootstrap CSS, router/forms) a schermo pulito — non prevede margine per le
pagine e i componenti che un progetto figlio aggiungerà. È deliberato: un figlio che monta qualcosa
di eager (un widget sempre visibile, un init globale, una libreria di stato) e fa scattare il
warning non ha "rotto" un limite dell'Engine — ha semplicemente superato il peso di partenza, ed è
lui a dover alzare `maximumWarning`/`maximumError` nel proprio `angular.json`, consapevolmente,
nello stesso commit che aggiunge il peso. Stesso principio delle estensioni additive di
`security-headers.override.json`: la base resta stretta apposta, l'allargamento è un'azione
esplicita e visibile in diff, mai un default permissivo che nasconde una regressione silenziosa (è
esattamente così che il warning è rimasto ignorato per mesi prima di questa sessione — budget largo
a sufficienza da non disturbare mai nessuno). Ogni volta che l'Engine stesso si avvicina di nuovo al
tetto, la causa va diagnosticata e risolta con lo stesso approccio (import statico → dinamico dove
il grafo lo permette), non con un innalzamento del numero.

`ImageLightboxService` (dietro `AssetDirective`/`LightboxDirective`) è iniettabile e apribile direttamente (`open(source, alt, returnFocusTo)`), utile per un trigger che non è l'`<img>` stesso — es. un bottone separato su un'immagine puramente decorativa (`alt="" aria-hidden`) che non deve restare l'unica affordance per aprire l'ingrandimento. Già documentato in [frontend/README.md](frontend/README.md), citato qui perché è un uso meno ovvio delle due direttive dichiarative.
